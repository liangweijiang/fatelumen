# FateLumen 深度解读基础数据与追溯规范

> 状态：B2 已实施事实快照持久化与管理端只读追溯（2026-08-28）  
> 权威关系：本文是 `FateLumen-开发任务书.md` 的专项规范；冲突时以开发任务书为准。  
> 当前范围：只建设完整报告。简单测算仅隐藏，代码、接口和数据结构保留，未来作为完整报告事实包的裁剪版恢复。
> 兼容策略：仅新生成报告在任何解读调用前写入不可变事实快照；旧报告不回填。调用记录表与查询界面已准备，调用写入留待下一阶段接入。

## 1. 目标与边界

完整报告必须形成一条可重放、可审计的链路：

```text
报告原始输入
→ 地点与历史时区
→ 真太阳时
→ lunar-go 确定性排盘
→ 基础规则计算
→ InterpretationFacts
→ 不可变事实快照
→ 分批 DeepSeek 调用记录
→ 10 章报告
```

- 四柱、十神、藏干、五行、强弱、喜忌、大运、流年和干支关系均由后端确定性计算。
- DeepSeek 只解释传入事实，不得重新排盘、修改年份、干支或规则结论。
- 每份报告保存独立快照；规则、Prompt或算法升级不得改变历史报告。
- B0只定义契约。数据库落表、接口实现和管理端页面在后续小块完成。

## 2. 数据分层

### 2.1 `ReportInputSnapshot`

只保存生成报告必需的输入：历法、年月日时分、闰月、性别、国家/地区/地点ID、经纬度、IANA时区、locale、档案联动方式及目标档案ID。

禁止保存：邮箱、电话、OAuth凭证、JWT、支付凭证、模型密钥。

### 2.2 `TimeCalculationSnapshot`

保存当地民用时间、历史/标准UTC Offset、DST、标准经线、经度修正、均时差、当地标准时间、平太阳时、真太阳时、自然跨日、换日规则以及地点/时区/太阳算法版本。

### 2.3 `ChartSnapshot`

保存当次报告实际使用的完整 `ChartData`、`chart_hash`、schema版本、排盘引擎版本和lunar-go版本。历史报告不得通过当前 `charts` 行反推快照。

### 2.4 `InterpretationFacts`

固定一级字段：

| 字段 | 来源 | 是否允许后台修改结果 |
|---|---|---|
| `input` | 报告请求归一化 | 否 |
| `time_calculation` | `BirthChartEngine` | 否 |
| `chart` | lunar-go与共享排盘引擎 | 否 |
| `element_strength` | 五行力量规则 | 仅后续通过版本化阈值配置 |
| `day_master_strength` | 得令/得地/得势规则 | 仅后续通过版本化阈值配置 |
| `ten_god_structure` | 十神力量规则 | 仅后续通过版本化阈值配置 |
| `stem_relations` | 天干确定性关系 | 否 |
| `branch_relations` | 地支确定性关系 | 否 |
| `pattern_candidates` | 格局候选规则 | 仅后续通过版本化规则配置 |
| `favorable_elements` | 喜忌规则 | 仅后续通过版本化规则配置 |
| `luck_cycles` | lunar-go | 否 |
| `annual_fortunes` | lunar-go及确定年份范围 | 否 |
| `chapter_facts` | 章节事实白名单 | 是，必须版本化发布 |
| `rule_matches` | 规则执行记录 | 否，只读追溯 |
| `warnings` | 完整性与冲突校验 | 否 |
| `versions` | 构建环境和规则版本 | 否 |

每个派生判断必须同时携带结果、分值/等级、参与柱位和符号、规则编码、来源、依据及冲突信息。

## 4. 版本与哈希

必须固定：`chart_hash`、`facts_hash`、`input_schema_version`、`chart_schema_version`、`facts_schema_version`、`rule_set_version`、`prompt_version`、`solar_algorithm_version`、`location_database_version`、`timezone_database_version`、`lunar_go_version`。

- 哈希输入使用UTF-8、稳定字段顺序、无无意义空白的规范JSON。
- `facts_hash`覆盖事实包全部确定性内容及所有版本，不覆盖数据库ID和生成时间。
- 任一规则或依赖版本变化必须产生新的 `facts_hash`。

## 5. 持久化草案（B0不执行）

### 5.1 `report_fact_snapshots`

```sql
CREATE TABLE report_fact_snapshots (
  id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  report_id BIGINT UNSIGNED NOT NULL,
  input_snapshot JSON NOT NULL,
  time_calculation_snapshot JSON NOT NULL,
  chart_snapshot JSON NOT NULL,
  facts_snapshot JSON NOT NULL,
  chart_hash VARCHAR(64) NOT NULL,
  facts_hash VARCHAR(64) NOT NULL,
  created_at DATETIME NOT NULL,
  UNIQUE KEY uk_report_fact_snapshot_report (report_id),
  INDEX idx_report_fact_snapshot_chart_hash (chart_hash),
  INDEX idx_report_fact_snapshot_facts_hash (facts_hash)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

报告创建后不可覆盖。需要用新规则重跑时创建新报告，不修改旧快照。

### 5.2 `report_llm_calls`

```sql
CREATE TABLE report_llm_calls (
  id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  report_id BIGINT UNSIGNED NOT NULL,
  batch_no INT NOT NULL,
  attempt_no INT NOT NULL,
  chapter_keys JSON NOT NULL,
  provider VARCHAR(32) NOT NULL,
  model VARCHAR(96) NOT NULL,
  system_prompt MEDIUMTEXT NOT NULL,
  user_prompt MEDIUMTEXT NOT NULL,
  input_facts JSON NOT NULL,
  raw_output MEDIUMTEXT,
  parsed_output JSON,
  schema_valid TINYINT NOT NULL DEFAULT 0,
  schema_errors JSON,
  parameters JSON NOT NULL,
  usage_data JSON,
  status VARCHAR(16) NOT NULL,
  error_summary VARCHAR(512),
  started_at DATETIME NOT NULL,
  finished_at DATETIME,
  duration_ms BIGINT,
  trace_id VARCHAR(64) NOT NULL,
  facts_schema_version VARCHAR(64) NOT NULL,
  rule_set_version VARCHAR(64) NOT NULL,
  prompt_version VARCHAR(64) NOT NULL,
  UNIQUE KEY uk_report_llm_attempt (report_id, batch_no, attempt_no),
  INDEX idx_report_llm_trace (trace_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

每次重试新增记录，禁止覆盖失败尝试。API Key和请求Authorization头绝不入库。

## 6. 管理端只读API契约（B0不实现）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/admin/reports/:id/facts` | 查看报告事实快照 |
| GET | `/api/v1/admin/reports/:id/llm-calls` | 分页查看全部批次和尝试 |
| GET | `/api/v1/admin/reports/:id/llm-calls/:callId` | 查看单次Prompt、输入、输出和校验结果 |

- 仅Admin Token可访问；C端Token必须被拒绝。
- 读取详情记录管理端审计日志。
- 响应不得包含密钥、认证头、邮箱、电话和支付凭证。

## 7. 管理端信息架构（B0不实现）

报告详情预留三个入口：`基础数据详情`、`DeepSeek调用记录`、`最终报告内容`。

- 基础数据详情：输入资料、时间换算、四柱、五行力量、十神、干支关系、强弱喜忌、大运流年、规则命中、版本哈希和警告。
- 调用记录：按Batch与Attempt展示状态、模型、耗时、token、Prompt、输入事实、原始输出、解析输出、Schema错误和trace_id。
- 大JSON支持折叠、格式化与复制，不在列表页直接展开。

## 8. 字段来源映射

| 数据 | 唯一来源 |
|---|---|
| 地点、经纬度、默认时区 | 固定地理基础库 |
| 历史Offset、DST | Go时区数据库/IANA规则 |
| 真太阳时 | `SolarTimeEngine` |
| 四柱、藏干、十神、纳音、大运、流年 | lunar-go及后端映射 |
| 五行力量、强弱、喜忌、干支关系 | 版本化确定性规则引擎 |
| 章节自然语言 | DeepSeek，只解释事实 |
| 最终PDF | 已校验的10章JSON |

## 9. 隐私与日志检查清单

- [ ] 事实包不含密码、JWT、OAuth凭证、API Key。
- [ ] DeepSeek输入不含邮箱、电话、支付资料。
- [ ] 业务日志不打印完整出生资料、命盘、Prompt或输出。
- [ ] 日志只记录report_id、call_id、batch、attempt、状态、耗时、哈希和trace_id。
- [ ] 管理端详情接口使用独立Admin鉴权。
- [ ] Prompt与输出只保存在受控数据库，不写普通日志。
- [ ] 导出或复制操作后续纳入审计日志。
