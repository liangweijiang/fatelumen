# FateLumen 深度解读基础数据与追溯规范

> 状态：B2 已实施事实快照持久化与管理端只读追溯；正式报告执行链 v2 已确认设计（2026-08-31）
> 权威关系：本文是 `FateLumen-开发任务书.md` 的专项规范；冲突时以开发任务书为准。  
> 当前范围：只建设完整报告。简单测算仅隐藏，代码、接口和数据结构保留，未来作为完整报告事实包的裁剪版恢复。
> 兼容策略：仅新生成报告在任何解读调用前写入不可变事实快照；旧报告不回填。调用记录表与查询界面已准备，调用写入留待下一阶段接入。

## 1. 目标与边界

完整报告必须形成一条可重放、可审计的链路：

```text
报告原始输入
→ 地点与历史时区
→ 真太阳时
→ lunar-go 确定性排盘
→ 基础规则计算
→ InterpretationFacts
→ 不可变事实快照
→ 分批 DeepSeek 调用记录
→ 10 章报告
```

- 四柱、十神、藏干、五行、强弱、喜忌、大运、流年和干支关系均由后端确定性计算。
- DeepSeek 只解释传入事实，不得重新排盘、修改年份、干支或规则结论。
- 每份报告保存独立快照；规则、Prompt或算法升级不得改变历史报告。
- B0只定义契约。数据库落表、接口实现和管理端页面在后续小块完成。

## 2. 数据分层

### 2.1 `ReportInputSnapshot`

只保存生成报告必需的输入：历法、年月日时分、闰月、性别、国家/地区/地点ID、经纬度、IANA时区、locale、档案联动方式及目标档案ID。

禁止保存：邮箱、电话、OAuth凭证、JWT、支付凭证、模型密钥。

### 2.2 `TimeCalculationSnapshot`

保存当地民用时间、历史/标准UTC Offset、DST、标准经线、经度修正、均时差、当地标准时间、平太阳时、真太阳时、自然跨日、换日规则以及地点/时区/太阳算法版本。

### 2.3 `ChartSnapshot`

保存当次报告实际使用的完整 `ChartData`、`chart_hash`、schema版本、排盘引擎版本和lunar-go版本。历史报告不得通过当前 `charts` 行反推快照。

### 2.4 `InterpretationFacts`

固定一级字段：

| 字段 | 来源 | 是否允许后台修改结果 |
|---|---|---|
| `input` | 报告请求归一化 | 否 |
| `time_calculation` | `BirthChartEngine` | 否 |
| `chart` | lunar-go与共享排盘引擎 | 否 |
| `element_strength` | 五行力量规则 | 仅后续通过版本化阈值配置 |
| `day_master_strength` | 得令/得地/得势规则 | 仅后续通过版本化阈值配置 |
| `ten_god_structure` | 十神力量规则 | 仅后续通过版本化阈值配置 |
| `stem_relations` | 天干确定性关系 | 否 |
| `branch_relations` | 地支确定性关系 | 否 |
| `pattern_candidates` | 格局候选规则 | 仅后续通过版本化规则配置 |
| `favorable_elements` | 喜忌规则 | 仅后续通过版本化规则配置 |
| `luck_cycles` | lunar-go | 否 |
| `annual_fortunes` | lunar-go及确定年份范围 | 否 |
| `chapter_facts` | 章节事实白名单 | 是，必须版本化发布 |

每个派生判断必须同时携带结果、分值/等级、参与柱位和符号、规则编码、来源、依据及冲突信息。

## 4. 版本与哈希

必须固定：`chart_hash`、`facts_hash`、`input_schema_version`、`chart_schema_version`、`facts_schema_version`、`rule_set_version`、`prompt_version`、`solar_algorithm_version`、`location_database_version`、`timezone_database_version`、`lunar_go_version`。

- 哈希输入使用UTF-8、稳定字段顺序、无无意义空白的规范JSON。
- `facts_hash`覆盖事实包全部确定性内容及所有版本，不覆盖数据库ID和生成时间。
- 任一规则或依赖版本变化必须产生新的 `facts_hash`。

## 11. 正式报告执行链 v2（已确认）

### 11.1 不可变边界

- 每次生成均创建新的 `report_id`；相同八字、相同客户、相同语言也允许再次生成，禁止复用或覆盖旧报告。
- 正式报告是一条完整流水线。管理端不得人工重跑、替换、删除单章或某次模型调用。
- 报告完成前允许系统按冻结策略自动重试；一次重试必须追加一条调用记录，禁止覆盖失败记录。
- `completed` 与 `failed` 均为终态。进入终态后，事实、编排、模型请求、模型响应、校验结果、最终章节和报告正文全部只读。
- 终态报告若需再次生成，只能创建新报告；可通过 `source_report_id` 记录来源，但新旧报告互不覆盖。
- 用户端不得交付部分完成报告。十章全部校验成功并完成汇总校验后，才能生成最终正文与 PDF。

完整状态流：

```text
pending
→ preflighting
→ generating
→ assembling
→ rendering
→ completed

任一不可恢复错误 → failed
```

### 11.2 自动预检

正式生成必须自动执行预检，任何入口都不得绕过。管理端可提供手动预检用于诊断，但必须复用同一个 `PreflightService`，手动结果不能替代正式执行时的自动预检。

阻断项：

- 计算档案、不可变计算版本或必要确定性事实不存在；
- 十章缺失、编号/章节键重复或最终指令为空；
- 章节输出协议无效；
- locale、Provider、模型路由、并发数、超时或自动重试策略非法；
- 无法生成冻结快照或快照哈希。

警告项不阻断：可选事实为空、专业译名缺失、指令偏长或非关键摘要为空。专业译名缺失时允许模型按命理语境翻译，并要求同一报告内保持一致。

预检结果必须写入执行快照，至少包含 `passed`、检查时间、阻断错误、警告和逐章结果。

### 11.3 数据冷热分层

列表、筛选、统计使用轻量元数据表；事实 JSON、Prompt、原始输出和最终正文进入独立 payload 表。列表 API 严禁读取 payload。详情页按标签懒加载，大字段通过唯一外键或一次 `IN (...)` 查询批量取得。

#### `full_reports`

保存报告级轻量元数据：用户/档案/订单关联、`source_report_id`、locale、状态、阶段、十章进度、模型路由键、冻结并发数、哈希、错误摘要、开始/完成/过期时间。不得保存事实快照、Prompt、原始模型输出或完整报告正文。

必要索引：

```text
(user_id, created_at, id)
(status, created_at, id)
(expires_at, status, id)
(facts_hash, created_at, id)
(source_report_id)
(order_id)
```

用户端和管理端列表采用 `(created_at, id)` 游标分页；数据量增长后禁止依赖大偏移量 `OFFSET`。

#### `full_report_execution_snapshots` 与 `full_report_execution_payloads`

`full_report_execution_snapshots` 每份报告唯一一条，仅保存版本、哈希和冻结时间。`full_report_execution_payloads` 通过 `snapshot_id UNIQUE` 保存：

- 原始输入、时间换算、命盘、完整事实包；
- 自动预检结果；
- 十章计划；
- 并发数、超时、自动重试、模型路由与模型参数的运行策略快照。

冻结后不得读取当前基础数据、Prompt、字典或系统配置重新解释历史报告。

#### `full_report_chapters` 与 `full_report_chapter_payloads`

每份报告在 `full_report_chapters` 固定十条轻量记录，唯一键：

```text
UNIQUE(report_id, chapter_no)
UNIQUE(report_id, chapter_key)
```

轻量表保存章节状态、尝试次数、最终采用的 attempt、Prompt/输出哈希、Schema与综合校验状态、错误摘要和时间。`full_report_chapter_payloads` 通过 `chapter_id UNIQUE` 保存语义摘要、语言附加指令、本章术语快照、最终实际 Prompt、输出 Schema、最终原始输出、最终解析输出及完整校验结果。

查询报告十章时先按 `report_id` 命中十条章节索引，再以一次 `WHERE chapter_id IN (...)` 批量读取 payload，禁止 N+1 查询。

#### `full_report_attempts` 与 `full_report_attempt_payloads`

每次真实模型请求新增一条 attempt 元数据；大字段通过 `attempt_id UNIQUE` 独立保存。唯一键：

```text
UNIQUE(chapter_id, attempt_no)
INDEX(report_id, chapter_id)
INDEX(trace_id)
INDEX(status, started_at)
```

元数据保存路由序号、Provider、模型、状态、校验摘要、token、耗时和 trace_id。payload 保存实际请求参数、完整实际 Prompt、原始输出、解析输出、Schema错误和完整校验结果。API Key、Authorization 与其他密钥禁止入库。

#### `full_report_validation_runs` 与 `full_report_validation_payloads`

每次十章报告汇总校验新增一条 validation run，不覆盖历史轮次。轻量表保存轮次、校验器版本、状态、是否可重试、受影响章节数量、错误摘要和起止时间；payload 通过 `validation_run_id UNIQUE` 保存完整逐规则结果、证据路径和受影响章节编号。

唯一键与索引：

```text
UNIQUE(report_id, round_no)
INDEX(status, created_at, id)
```

最终完成事务必须确认该报告最新一轮汇总校验为 `passed`。失败轮次在报告进入终态后仍只读可查，供管理端还原校验和系统重试过程。

#### `full_report_results`

每份成功报告唯一一条，通过 `report_id UNIQUE` 保存最终十章 JSON、完整正文、内容哈希、渲染版本、PDF对象 key 和 PDF 哈希。PDF 文件进入对象存储，数据库不保存二进制文件。

### 11.4 并行与模型路由

- 十章必须支持受控并行，`chapter_concurrency` 可配置为 1～10，默认值由环境配置决定。
- 报告开始时把并发、超时、自动重试和完整模型路由复制进运行策略快照；后续配置变化只影响新报告。
- 每章独立执行、独立校验、独立自动重试。任一章节最终失败则整份报告失败，不交付其余成功章节。
- 模型路由为有序列表，每个路由包含 Provider、模型、最大尝试数、超时和非敏感参数。首选路由耗尽后允许切换后备路由，业务层只依赖 `LLMProvider`。
- 网络错误、限流、非法 JSON、Schema失败、模块遗漏、确定性事实冲突和产品边界违规可按冻结策略重试；确定性输入自身缺失不得通过更换模型掩盖。

### 11.5 校验器链

所有章节必须通过统一、可扩展的 `ChapterValidator` 链：

1. **格式校验**：单一合法 JSON、无 Markdown 包裹、无前后附加说明、编码/大小/深度合法。
2. **Schema校验**：章节键正确、固定模块齐全、字段类型正确、必填内容非空、无非法顶级字段。
3. **完整度校验**：模块达到最低内容要求，无占位敷衍、大面积重复或所有模块同文。
4. **事实一致性校验**：四柱、日主、性别、强弱、喜用、大运、流年年份和干支不得违背冻结事实。
5. **语言与术语校验**：正文主体语言符合 locale；JSON key 不翻译；指定术语在同一报告内一致；中文干支允许保留。
6. **产品边界校验**：禁止绝对寿命、医学诊断、具体投资操作、收益保证和内部指令泄露。
7. **报告汇总校验**：十章齐全且各自成功，章节编号唯一，关键结论跨章一致，十年流年范围连续一致。

校验失败必须保存结果并追加新 attempt。能定位到章节的汇总错误只重新生成涉及章节；自动策略耗尽后整份报告进入 `failed`。管理员不提供人工单章重试入口。

### 11.6 原子完成与防篡改

完成事务必须：校验十章全部成功、保存最终报告、保存内容哈希、写入完成时间并把状态更新为 `completed`。所有执行更新必须附带非终态条件；终态报告不得追加 attempt 或修改章节 payload。

至少保存：

- `facts_hash`：确定性事实及其版本；
- `execution_hash`：十章实际指令、术语、输出协议、模型参数与运行策略；
- `content_hash`：十章最终解析结果和完整报告。

管理端读取时可重新计算哈希做完整性检查。不得为终态表提供通用编辑接口。

### 11.7 管理端增删改查边界

管理端提供只读列表和详情：报告总览、基础数据、编排快照、十章并行时间线、系统自动尝试、原始/解析输出、校验结果、最终报告和 PDF。列表只查轻量表，大字段展开时再读取。

管理员可以按授权删除整份报告或基于原资料创建新报告；不得修改终态事实、Prompt、章节、输出、最终采用 attempt，也不得单独删除失败尝试。生成过程中的状态更新仅由系统状态机执行。

### 11.8 保留与清理

保留期通过 `retention_policy + expires_at` 在报告创建时固化，不在代码中写死 30 天或 180 天。到期清理由后台任务按小批次执行：对象存储 → attempt payload → attempt metadata → validation payload → validation metadata → chapter payload → chapter metadata → execution payload → execution metadata → result。删除过程中报告标记 `deleting`，禁止查询到残缺链路。

订单与支付按独立财务策略保存。报告内容到期后可仅保留匿名最小记录和删除时间，不再保留出生资料、Prompt、模型输出或 PDF。第一版不启用 MySQL 分区；先依靠拆表、覆盖索引、游标分页和批量清理，达到实际千万级调用记录后再评估按月分区。
